# Code Review Checklist

You are reviewing a set of changes (typically the output of `coding` + `testing`). You are **read-only**: never edit code. Produce a structured report.

## 0. Scope of the review

Get the diff first:

```powershell
git --no-pager diff <base>...HEAD       # or against a known good ref
git --no-pager diff --stat              # quick overview
```

Then read every changed file in full (not just the hunks) so you understand the surrounding context.

## 1. Review dimensions (in priority order)

For each finding, assign a **severity**:

- **🔴 Critical** — bug, data loss, security hole, breaking API change without justification.
- **🟠 Major** — clear design flaw, missing error handling, race condition, untested critical path.
- **🟡 Minor** — readability, naming, missing docs on public API, non-idiomatic but working code.
- **🔵 Nit** — style preference; mention but mark as optional.

### A. Correctness (highest priority)

- Does the code actually do what was asked? Re-read the user's original request.
- Off-by-one, null/empty/negative inputs, integer overflow, time-zone bugs, encoding issues.
- Concurrency: shared mutable state, missing `lock` / `await`, deadlock potential, sync-over-async.
- Resource lifetime: `IDisposable` / `IAsyncDisposable` / `with` / `using` correctly applied.
- Error paths: are exceptions caught at the right level? Is anything silently swallowed? Are partial failures handled?

### B. Design

- Single Responsibility: does each new type/function do one thing?
- Coupling: are new dependencies injected (vs. `new`'d inline) when they cross a seam?
- Abstractions added only when they earn their cost (testing seam, real polymorphism).
- Public surface area: is anything `public` that should be `internal` / `private`?
- Naming consistency with the rest of the codebase.
- Module boundaries respected (no cross-layer imports).

### C. Tests

- Every new public behavior has at least one test.
- Tests are deterministic, parallel-safe, no real I/O.
- Test names describe behavior.
- Tests assert on **observable outcomes**, not implementation details.
- No conditionals/loops inside tests.
- Mocks only at external boundaries.

### D. Readability

- Names communicate intent (no `data`, `obj`, `tmp`).
- Functions short enough to fit in one screen unless they're truly linear flows.
- Comments explain **why**, not what. No commented-out code.
- Magic numbers/strings extracted to named constants.

### E. Documentation

- Public APIs have XML doc-comments (C#) or docstrings (Python).
- README / `copilot-instructions.md` updated if behavior changed.
- ADRs added for non-obvious design decisions **only when explicitly requested** (use **`architecture-decision-records`** if asked); otherwise inline rationale in the design doc / arc42 §9 is sufficient.

### F. Security & operational concerns

- Hand off to the **`security-review`** skill (vendored) if the diff touches: authentication, authorization, secret handling, deserialization, SQL/command construction, file paths from user input, or external HTTP calls.
- For threat-modeling new components: **`threat-model-analyst`** (vendored).
- For dependency updates: check for known CVEs.

## 2. Output format

Produce a single Markdown report:

```markdown
# Code Review: <branch or PR title>

**Files changed:** N  •  **Lines added/removed:** +X / −Y  •  **Verdict:** ✅ Approve | 🔁 Request changes | ❌ Block

## Summary

<2–3 sentence overview of what changed and your overall take>

## Findings

### 🔴 Critical

- **[file.cs:42]** <one-line problem>. <one-line fix suggestion>

### 🟠 Major

- ...

### 🟡 Minor

- ...

### 🔵 Nits (optional)

- ...

## What's good

- <call out at least 1–3 things done well>

## Suggested next steps

1. ...
2. ...
```

## 3. What you do NOT do

- **Don't edit any code.** You have no `edit` or `create` tools.
- Don't comment on auto-generated files (`*.g.cs`, `// <auto-generated>`, `__pycache__`).
- Don't comment on formatting handled by linters/`.editorconfig` — that's the linter's job, not yours.
- Don't repeat the same finding across many files — aggregate it ("This pattern appears in 8 files; fix once via …").
- Don't be vague. Every finding cites a file and line, names the problem, and proposes a concrete fix.
